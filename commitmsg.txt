Sprint 8: analytics and reporting, plus the dead wait-estimate column

Admin reports (/admin/reports) with a CSV export, on a new ReportingService:
headline figures, wait and service time, demand against capacity per service,
per-window performance, arrivals by hour, daily trend, RA 9994 / RA 10754
compliance, and cancellation reasons. Period chosen by preset or explicit dates.

Bug: estimated_wait_minutes was a dead column.

The appointments table had a fillable, cast estimated_wait_minutes column that
nothing ever wrote to. The estimate was computed on the fly for the live display
and discarded, so there was no record of what a client was actually told - and "how
good is our wait estimate?", the question a queue system is judged on, could not be
answered at all.

QueueService::checkIn() now stores it. Check-in is the honest moment:
actualWaitMinutes() measures checked_in_at -> serving_started_at, so the figure
recorded is measured over exactly the window the client was promised. Booking alone
records nothing, because a slot booked for next week has no meaningful wait yet.

Three reporting rules, each learned from a wrong number:

- No data is null, never zero. "Average wait 0 minutes" reads as "we served
  everyone instantly". Every average carries its sample size, anything under 5 is
  labelled indicative only, and a rate with no denominator is null rather than 0%.
- One date key per question. My first version counted demand by created_at while
  capacity came from slot_date, and printed "Booked 27, places offered 1600,
  utilisation 0%" - two unrelated sets of days. Bookings made and tickets that
  belonged to a day are now separate labelled figures, and anything compared
  against a slot calendar uses queue_date.
- Occupancy is not demand. booked_count is current occupancy, and a slot releases
  its place the moment a client is served, so every slot in a past window reads as
  empty and "did we run out?" always answers no. Utilisation is demand over supply;
  "slots filled" counts slots where appointments ever attached reached the ceiling.

Priority refusals are read from the audit trail rather than from appointments.
refusePriority() deliberately clears all three claim flags - correct for queue order,
since a refused claim must stop granting precedence immediately - but it makes a
refused claim indistinguishable from never having been made. The audit log is the
only place the decision, the reason, and the staff member survive.

Also fixed:

- The CSV export wrote to a php://output handle and then handed that same handle
  to streamDownload(), which would send an already-closed stream: an empty file
  with a 200. Built into a string instead.
- Cancellation reasons excluded '' but not whitespace, so a stray space typed into
  the form became a meaningless top row. TRIM now applied in the query.
- Carbon 3 returns a float from diffInDays, so a custom reporting period came back
  as 30.0 where callers expect an int.
- ServiceFactory used fake()->unique()->randomElement() over a five-item pool, so
  it threw OverflowException after five services in one process. Names need no
  uniqueness; only the code does.

I also investigated a suspected booked_count inconsistency in the seeded data and
found none: my probe had counted completed and cancelled tickets, which correctly
no longer occupy a slot. No change made, because there was no bug.

522 tests passing (was 479). Pint clean. Accessibility audit clean across 24 pages.
